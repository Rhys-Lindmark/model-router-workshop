And if you knew in advance which model each prompt needed, you’d beat the large model on accuracy at a sixth of its cost. That gap is what a router is for.
The obvious move

Ask an LLM: “Which model should I use?”

// One typed question to Jev, a small model that answers with probabilities
model_choice: {
  type: 'choice',
  instructions: 'Which model should I use for this prompt?',
  criteria: { Haiku: 'Claude Haiku', Sonnet: 'Claude Sonnet',
              Opus: 'Claude Opus', Fable: 'Claude Fable' }
}

// "How many months from 1953 through 1988 have a Friday the 13th?"
→ Opus 0.46   Sonnet 0.32   Haiku 0.18   Fable 0.04

It works. It’s one line. Most of us ship this first.

The anti-pattern3
Here’s the version I wrote first. One question, four options, take the top answer. It runs, it gives sensible-looking picks, and you can ship it in an afternoon. On this prompt, a long date-counting problem, it says Opus. Let’s look at why that’s a trap.
Why it’s worse

You’ve asked the model to make your decision.

  • Policy hides in the model. Cost, speed and quality trade-offs live in its weights, not in code you can read and test.
  • The options are just labels. “Opus” describes nothing about the prompt. The answer depends on what the model happens to know about Opus.
  • It fails the human test. Show a smart person only this question and they’d ask, “Do you care about cost or quality?”
  • Nothing to change but the wording. No thresholds, no rows. New policy means a new prompt.
The anti-pattern4
Four problems. The one I’d underline is the human test: if a smart colleague couldn’t answer the question from the prompt alone without asking what you care about, the model can’t either. It just guesses, confidently.

Ask for judgments a smart person could make from the prompt alone. Keep the decision where you can see it.

Jev: typed questions in, calibrated probabilities out · docs.typesafe.ai5
Split the job. The model answers small factual questions about the prompt: does a right answer depend on exact digits? Does it need a long procedure? Those are judgments anyone could make from the prompt alone. Then a table in code turns the judgments into a model and an effort level. I’m using Jev from TypeSafe, which answers typed questions with probabilities, but the pattern works with any model that can give you calibrated yes/no answers.
Step 1 · Questions

Judgments are typed questions.

// src/questions.js: one request, every question at once
reasoning_depth: { type: 'score', instructions: 'How much working out does a good answer to `prompt` take?',
                   criteria: ['None…', 'A few steps…', 'A plan…', 'Long, careful reasoning…'] },
expertise:       { type: 'noul',  instructions: 'Does answering `prompt` well take specialist expertise?' },
high_stakes:     { type: 'noul',  instructions: 'Could a wrong answer to `prompt` cause real harm or cost?' },
large_output:    { type: 'noul',  instructions: 'Does `prompt` ask for a large piece of work?' },
nuanced_writing: { type: 'noul',  instructions: 'Does `prompt` ask for writing where tone and style matter?' }

POST https://api.typesafe.ai/v1/systemone   { state: { prompt }, questions }
→ { reasoning_depth: { probabilities: { 0: .01, 1: .46, 2: .38, 3: .15 } }, expertise: { noul: .12 }, … }

No model names, no prices. Just facts about the prompt.

Router v1’s five questions · Noul = a yes/no question answered with a probability6
Router v1 asked five questions. A Score for how much reasoning the prompt takes, and four yes/no questions, which Jev calls Nouls. Notice none of them mentions a model or a price. They’re all about the prompt. One HTTP call asks all of them at once.
Step 2 · Code

Policy is a file, not a prompt.

// src/policy.js: ordered rows, first match wins, the last row always matches
export const ROUTER_V1 = [
  { test: j => j.large_output,               tier: 'opus' },
  { test: j => j.depth === 3,                tier: 'opus' },
  { test: j => j.expertise && j.depth >= 2,  tier: 'opus' },
  { test: j => j.expertise && j.high_stakes, tier: 'opus' },
  { test: j => j.expertise,                  tier: 'sonnet' },
  { test: j => j.depth === 2,                tier: 'sonnet' },
  { test: j => j.nuanced_writing,            tier: 'sonnet' },
  { test: j => j.high_stakes,                tier: 'sonnet' },
  { test: () => true,                      tier: 'haiku' }  ← Friday the 13th
];

Change routing by editing a row. Review it in a PR. Test it.

Plus a 7-row table for effort · on the live page rows 1–2 pick Fable; the eval’s top tier is Opus7
And here’s the decision, in code. Rows in order, first match wins. You can read every reason a prompt went where it went. This looked very sensible to me when I wrote it. Expertise and stakes feel like the things that should cost more. Our Friday-the-13th prompt needs no expertise and has no stakes, so it falls all the way through to the small model. Hold that thought.

Does it work?

Run every model on every prompt. Grade by code.

228

prompts in math, code, writing, logic and facts. Every answer checked by code: computed answers, hidden tests, “exactly 12 words”. No LLM judge.

6

options per prompt: three sizes of one model family × low and high reasoning effort. So any policy can be scored on the same runs.

60 / 168

train / held-out. Router v2 was built from the 60. Every score you’ll see is on the 168.

Score each router next to fixed choices, perfect routing and random routing with the same mix of picks. Total cost: $15.

Method: TypeSafe’s SDE cascade cookbook + Baseten’s router write-up9
The eval is the part I’d want you to steal. Run every option on every prompt once, grade it by code, and then scoring any routing policy is a lookup: free and instant. That’s why the repo can score your router in under a second with no keys. The random baseline matters: deal the same mix of models to prompts at random ten thousand times. If your router can’t beat that, it isn’t routing, it’s just a price mix.

Router v1, the table I showed you, is down at 80%. So the first table was wrong. Here’s how the eval told us why.
What the eval taught us

Models didn’t fail on expertise or stakes.
They failed on exact details and long procedures.

Router v1’s 28 “too weak” picks

Calendar prompts counting days across years. Letter counts. “Write 40 words without the letter e”. Exact multiplication. Short functions.

None needs expertise. All look shallow. A small model gets them wrong.

So Router v2 asks four new questions

exact_details   Does a correct answer depend on
                exact letters, words or digits?
long_procedure  Does it need a long procedure,
                step by step?
quick_recall    One well-known fact or one step?
writes_code     Does it ask for code?

Written from the 60 training prompts only. The fix was better questions, not better thresholds: the best re-tune of v1’s thresholds reached 87.5%, at $5.62.

v1 verdicts: right 69 · more than needed 66 · too weak 28 · nothing passes 511
Comparing each v1 pick with the cheapest option that passed showed a clear pattern. Its misses weren’t expert questions. They were prompts where one wrong letter or digit makes the answer wrong, and long procedures like counting dates across decades. My questions about expertise and stakes couldn’t see that. So v2 asks about it directly. Notice what didn’t work: twiddling v1’s thresholds. When the questions are wrong, no table fixes them.
Router v2

The table, built from the eval.

// src/policy.js · first match wins · yes means probability ≥ 0.5
export const ROUTER_V2 = [
  { when: 'Exact details and a long procedure',          option: 'sonnet:high' },
  { when: 'Exact details, quick recall or no reasoning', option: 'haiku:high' },
  { when: 'Exact letters, words or digits',              option: 'sonnet:high' },
  { when: 'Long step-by-step procedure',                 option: 'sonnet:high' },
  { when: 'Large piece of work',                         option: 'opus:low' },
  { when: 'Writes code',                                 option: 'haiku:high' },
  { when: 'Quick recall',                                option: 'haiku:low' },
  { when: 'Otherwise',                                   option: 'sonnet:low' }
];

Limits: one run per prompt · open stand-in models · graded puzzles, not real traffic13
I want to be straight about this. On these prompts, always using the medium model at high effort scores the same as the best router. You only know that because you ran the eval. That’s the real lesson: the eval told me which fixed choice was right, and a router is how you keep making that call when the prompts change. If you take one thing from this, run every option on your own traffic before you build anything clever.

Takeaways

Three things to steal.

  • Ask for judgments, not decisions. Questions a smart person could answer from the prompt alone. Keep cost and quality trade-offs in code.
  • Put policy in a file the eval imports. Then the eval scores exactly what ships, and a routing change is a diff.
  • Score against fixed, perfect and random. Without them, any router looks good. With them, you might find you don’t need one.
